AI-01 工程骨架：从类图到目录
====================================================================
AI-01-L001 场景：把实验二的类图和三张核心需求贴给大模型，要求给出 Python 工程目录与文件职责。
AI-01-L002 提示词（摘录）：
AI-01-L003   “下面是一个酒店预订系统的 UML 类图。请把它实现成 Python 工程，
AI-01-L004    给出目录结构、每个文件的职责，以及类与文件的对应关系。”
AI-01-L005 生成结果：平铺 12 个 .py 文件（models.py、services.py、db.py、ui.py…），
AI-01-L006   services 里直接 import sqlite3、拼 SQL、弹 messagebox；
AI-01-L007   领域实体是 dict，状态用字符串字面量，没有枚举。
AI-01-L008 人工判断：
AI-01-L009   这样写能跑，但三件事会立刻出问题：
AI-01-L010   一是规则没法单测（要起窗口、连数据库）；
AI-01-L011   二是 SQL 散在业务里，改一处库存口径要全文搜；
AI-01-L012   三是“事务边界”会跟着 if/else 走，日志和业务很难同事务。
AI-01-L013 修改：
AI-01-L014   改成四层：domain（纯规则）、application（用例）、infrastructure（SQLite）、ui（Tkinter）。
AI-01-L015   domain 不 import sqlite3；application 只依赖仓储门面；ui 只调 application。
AI-01-L016   依赖方向用 import 约束住，测试里用 `build(":memory:", FixedClock(...))` 组装。
AI-01-L017 优点：目录和职责一次给全，省了从零想分层的时间。
AI-01-L018 缺点：它默认“能跑就行”，不会主动考虑可测试性与依赖方向。

AI-03 库存扣减：先查后扣
====================================================================
AI-03-L001 场景：让大模型写“订 3 晚、每晚扣库存”的代码。
AI-03-L002 提示词（摘录）：“每个日期查剩余库存，够就扣，不够返回售罄，注意事务。”
AI-03-L003 生成结果：
AI-03-L004   `row = SELECT remaining FROM inventory WHERE ...`
AI-03-L005   `if row.remaining >= n: UPDATE inventory SET sold = sold + n`
AI-03-L006   循环三晚；失败时 `return False`，但前两晚已经 UPDATE 了。
AI-03-L007 人工判断：
AI-03-L008   这是典型 TOCTOU：两个请求都读到 1 间，都判断“够”，都扣，最后 sold=2、total=1。
AI-03-L009   而且失败只 return，没有回滚，前两晚的库存会永久少掉。
AI-03-L010 修改：
AI-03-L011   改成一条条件 UPDATE：
AI-03-L012     `UPDATE daily_inventory SET sold_rooms = sold_rooms + ?
AI-03-L013      WHERE room_type_id=? AND day=? AND stop_sale=0
AI-03-L014        AND sold_rooms + ? <= total_rooms`
AI-03-L015   rowcount=0 即售罄；整段放在 `with db.transaction()` 里，任一晚失败抛异常回滚。
AI-03-L016   用 50 个线程抢 1 间房验证：成功 1 单、49 个 SOLD_OUT、库存 1。
AI-03-L017 优点：SQL 语法和事务框架写得很快，注释也清楚。
AI-03-L018 缺点：默认“查询—判断—写入”是原子的；不加提示绝不会主动写条件 UPDATE。

AI-05-L002 提示词（摘录）：“18:00 前免费取消，18:00 后收首晚；未入住收首晚；提前退房退未住间夜。”
AI-05-L003 生成结果：
AI-05-L004   取消用 `if now.hour < 18`；未入住“释放全部库存、全额退款”；

AI-05-L008   未入住只释放入住日之后，首晚要保留；提前退房只释放退房日当晚起、原退房日前；
AI-05-L009   退款金额必须逐晚小计，不能用比例或平均价。
AI-05-L010 修改：
AI-05-L011   单独写 `cancellation.py`，三个纯函数返回 `RefundQuote(event, deducted, refundable)`；
AI-05-L012   用 `datetime.combine(check_in, time(18, 0), tzinfo=HOTEL_TZ)` 做边界，
AI-05-L013   测试钉在 17:59:59 / 18:00:00 / 18:00:01 三个时刻；
AI-05-L014   未入住 `stay_dates[1:]`，提前退房 `day >= actual_check_out`。
AI-05-L015 优点：能把规则写成短函数，变量命名也规范。
AI-05-L016 缺点：边界条件（<= 还是 <、含不含当天）几乎每次都要人工改。

AI-06-L002 提示词（摘录）：“用订单号做幂等键；2 分钟内相同内容提示重复；并发重放只建一单。”

AI-06-L004   用 `order_no` 做幂等键（但 order_no 是服务端生成的，客户端拿不到）；

AI-06-L007 人工判断：
AI-06-L008   幂等键必须是客户端生成的 `(user_id, request_id)`，且由数据库唯一约束兜底；
AI-06-L009   窗口是 2 分钟，含 2:00；比较内容要包含酒店、房型、日期、间数、入住人；
AI-06-L010   二次确认前不能创建新单，确认后才允许。

AI-06-L012   schema 加 `UNIQUE(user_id, request_id)`；事务内再查一次幂等；

AI-06-L014   抛 `DuplicateOrder`，界面弹“仍然创建”，重提时带 `confirm_duplicate=True`；
AI-06-L015   测试：同一 request_id 重放返回同一 id，不同 request_id 同内容先 409、确认后建第二单。
AI-06-L016 优点：能快速给出“先查后插”的骨架。
AI-06-L017 缺点：并发下的“查—插”竞态不会主动处理，唯一约束也不会主动加。

AI-09 测试：并发用例的假成功
====================================================================
AI-09-L001 场景：让大模型写 pytest，包括 REQ-029 的 50 并发抢房。
AI-09-L002 提示词（摘录）：“写 50 个线程同时下单，断言只有一个成功。”
AI-09-L003 生成结果：10 个线程；所有线程共用同一个 request_id；
AI-09-L004   只断言“成功数<=1”，没有断言库存和订单数；
AI-09-L005   时间直接 `datetime.now()`，没有固定时钟。
AI-09-L006 人工判断：

AI-09-L008   只断言 <=1 的话，全失败也能通过；必须断言恰好 1 单、库存=1、其余全是 SOLD_OUT；

AI-09-L010 修改：
AI-09-L011   每个线程独立 request_id；`ThreadPoolExecutor(max_workers=50)`；
AI-09-L012   断言 `len(success)==1`、`sold==1`、其余异常类型都是 SoldOut；
AI-09-L013   引入 `FixedClock`，覆盖 17:59:59/18:00:00/18:00:01 与 23:59/00:00；

AI-09-L015 优点：测试骨架、fixture 组织、断言写法很省时间。
AI-09-L016 缺点：并发用例经常“看起来在测并发，其实在测幂等”，必须自己检查请求键。

人工审查清单（CHK-01～CHK-16）
====================================================================
CHK-01 金额是否全部整数分、是否有 float              → 通过（schema 与实体均为 int cents）
CHK-02 日期是否左闭右开、退房日是否不计库存          → 通过（stay_dates 用 range(check_in, check_out)）
CHK-03 逐晚扣减是否原子、失败是否整单回滚            → 通过（条件 UPDATE + 事务 + 50 线程用例）
CHK-04 订单状态是否 7 个、是否存在禁止转换            → 通过（TRANSITIONS 7 条，禁止转换用例）
CHK-05 确认前是否复核库存、停售是否只能拒绝          → 通过（_assert_stock_confirmable）
CHK-06 18:00 边界是否 18:00:00 免费、18:00:01 收费    → 通过（FixedClock 三点用例）
CHK-07 未入住是否只释放首晚之后、首晚是否保留        → 通过（stay_dates[1:]）
CHK-08 提前退房是否只释放未住间夜、是否需店长        → 通过（release_days_after + 角色校验）
CHK-09 幂等键是否 (user_id, request_id) 且有唯一约束  → 通过（schema UNIQUE + 事务内二次查）
CHK-10 2 分钟重复是否含入住人比较、是否可二次确认    → 通过（guest 集合 + confirm_duplicate）
CHK-11 越权是否 403/404、跨酒店是否不泄露存在性      → 通过（resolve_order + NotFound）
CHK-12 日志是否与业务同事务、手机号是否脱敏          → 通过（write_log 在事务内，mask_phone）
CHK-13 报表 8 项口径是否与 REQ-018 一致               → 通过（no-show/迟到取消用例手算对拍）
CHK-14 定时任务是否可拨时钟、是否重复执行安全        → 通过（SchedulerService.run + 固定时钟）
CHK-15 密码是否非明文、失败提示是否不泄露账号存在    → 部分通过（PBKDF2 替代 bcrypt，见 7.2）
CHK-16 报告数字是否可回溯、是否无编造                → 通过（行数/覆盖率/测试数均来自命令输出）
